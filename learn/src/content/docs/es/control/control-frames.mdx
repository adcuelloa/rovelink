## El problema

El navegador mantiene un `ControlState` — throttle, steering, pinza, armed. El robot necesita recibir ese estado por la red. Pero ¿cómo se ve el mensaje real? ¿Qué campos lleva? ¿Quién agrega qué?

Un enfoque ingenuo sería simplemente enviar `{ throttle: 0.5, steering: 0.3 }` por el WebSocket. Pero eso crea preguntas difíciles:

- ¿Cómo sabe el firmware que este frame es más nuevo que el anterior?
- ¿Cómo sabe que el frame no expiró en tránsito?
- ¿Cómo sabe que el frame pertenece a la _sesión actual_ de control y no a un eco retrasado de una sesión que terminó hace diez segundos?

Sin respuestas a estas preguntas, el robot aplicará comandos obsoletos, comandos duplicados, o comandos de la sesión equivocada. El protocolo necesita un sobre — un frame que lleve metadata junto con el estado de conducción.

## La idea

Un `ControlFrame` es un sobre versionado de JSON que envuelve el estado de conducción con metadata para ordenamiento, expiración, y vinculación de sesión. Cada frame que el navegador envía tiene la misma estructura. Cada frame que el firmware recibe tiene la misma estructura. El relay en el medio estampa un campo extra. Este es el contrato que mantiene al navegador, relay, y firmware de acuerdo sobre lo que el robot debe estar haciendo ahora.

## La forma del frame

Acá está la interfaz completa de `ControlFrame` desde `protocol.ts`:

```typescript
{
  v: 1,                    // versión del protocolo
  type: 'control',         // tipo de mensaje
  seq: number,             // número de secuencia monotonamente creciente
  sentAt: number,          // Date.now() al momento de enviar
  ttlMs: number,           // time-to-live, por defecto 500ms
  throttle: number,        // -1..1
  steering: number,        // -1..1
  gripper: Gripper,        // 'idle' | 'open' | 'close'
  armed: boolean,
  controlSessionId?: string // agregado por el relay, NO por el navegador
}
```

Todos los campos son requeridos excepto `controlSessionId`, que es opcional en el cable (presente en los frames que reenvía el relay, ausente en los frames que envía el navegador). El frame extiende `ControlState`, así que lleva los cuatro ejes de conducción más los campos de metadata.

## Campo por campo

**`v = 1`** — Versión del protocolo. El firmware está grabado en un chip y no se puede actualizar trivialmente. El campo de versión permite que el formato del cable evolucione sin romper el firmware desplegado. Si el formato del frame cambia en una versión futura, el firmware puede revisar `v` y rechazar mensajes que no entienda.

**`type = 'control'`** — Distingue este mensaje de otros tipos de mensaje: `telemetry`, `ping`, `pong`, `emergency-stop`, `controller.session`, y otros. El relay y firmware usan `type` para enrutar el mensaje al handler correcto.

**`seq`** — Un número de secuencia monotonamente creciente. El firmware usa `isNewerFrame()` para rechazar frames obsoletos, duplicados, y reordenados. Si el firmware ya procesó `seq: 183`, rechazará `seq: 182` aunque ese frame llegue después. Esta es la defensa principal contra el reordenamiento de red.

**`sentAt`** — `Date.now()` al momento de enviar. El helper `isFrameExpired(frame, now)` del paquete de protocolo puede usar este campo para calcular el TTL — y eso es lo que usan el transporte simulado del navegador y el simulador de este sitio. **El firmware real del ESP32 no lo hace** — nunca lee `sentAt` al aplicar un frame. Ver [TTL y Watchdog](/es/safety/ttl-watchdog/) para lo que el firmware realmente verifica.

**`ttlMs = 500`** — Viaja con el frame por la misma razón que `sentAt`: es lo que usan `isFrameExpired()` y el simulador, no lo que lee el firmware. El firmware tiene su propia constante `TTL_CONTROL_MS` (también 500ms), definida por separado y mantenida sincronizada a mano — ver [TTL y Watchdog](/es/safety/ttl-watchdog/).

**`throttle`, `steering`, `gripper`, `armed`** — El estado de conducción real. Estos son los valores que el firmware aplica a los motores. El rango para `throttle` y `steering` es -1..1, `gripper` es uno de `'idle'`, `'open'`, `'close'`, y `armed` es un booleano.

**`controlSessionId`** — Este es el campo crítico. El navegador **nunca** lo setea. No tiene autoridad para declarar su propia sesión. El relay lo estampa en cada frame que reenvía al dispositivo, desde el ID de sesión que generó cuando ese controlador fue promovido. Esto previene que frames retrasados de sesiones antiguas se cuelen de vuelta.

## Frames del navegador vs. relay vs. dispositivo

El mensaje cambia de contexto de propiedad a medida que viaja:

```
BROWSER construye:
  { v, type, seq, sentAt, ttlMs, throttle, steering, gripper, armed }

RELAY estampa:
  + controlSessionId (de la sesión autoritativa)

DISPOSITIVO recibe:
  { ...browser frame, controlSessionId }
```

El navegador es la autoridad sobre _qué_ debe hacer el robot. El relay es la autoridad sobre _quién_ tiene permitido comandarlo. Ninguno puede hacer el trabajo del otro. El navegador no puede generar IDs de sesión porque no sabe qué sesión considera autoritativa el relay. El relay no puede inventar valores de throttle porque no sabe qué está comandando el operador. El frame es el punto de transferencia entre estas dos autoridades.

## Números de secuencia — por qué existen

Los paquetes de red no siempre llegan en orden. Acá hay un ejemplo concreto:

```
Paquete 181: throttle 0.5  — enviado primero, llega tercero
Paquete 183: throttle 0.8  — enviado tercero, llega primero
Paquete 182: throttle 0.3  — enviado segundo, llega segundo
```

El firmware los recibe en el orden: 183, 182, 181. Sin números de secuencia, aplicaría cada uno en orden de llegada, terminando en throttle 0.5 — el _primer_ comando enviado, no el _último_.

Con números de secuencia, el firmware llama a `isNewerFrame()` para cada uno:

```
Frame 183: seq 183 > lastSeq 0  → aceptado. lastSeq = 183
Frame 182: seq 182 < lastSeq 183 → rechazado (obsoleto)
Frame 181: seq 181 < lastSeq 183 → rechazado (obsoleto)
```

El robot aplica throttle 0.8 — el último comando que el operador realmente envió. Los comandos viejos se descartan. Esto es exactamente cómo funciona `isNewerFrame()` en el código fuente:

```typescript
export const isNewerFrame = (frame: ControlFrame, lastSeq: number): boolean => frame.seq > lastSeq;
```

Mayor estricto. Una retransmisión del mismo seq también se rechaza. El seq más alto siempre gana.

## TTL — un campo con dos consumidores distintos

`protocol.ts` define un helper que compara `sentAt` y `ttlMs` contra el tiempo actual:

```typescript
export const isFrameExpired = (frame: ControlFrame, now: number): boolean =>
  now - frame.sentAt > frame.ttlMs;
```

Este helper es real y se usa — por el transporte simulado del navegador (`web/src/transport/mock.ts`) y por el simulador de este sitio. **No se llama en ningún lugar del firmware del ESP32.** Esta es una brecha preexistente entre el paquete de protocolo y la implementación del firmware, no algo para memorizar como comportamiento del dispositivo.

El watchdog real que protege al robot físico vive enteramente en el dispositivo y no toca este campo — compara su propio reloj contra la última vez que llegó _cualquier_ frame válido, sin importar lo que dijera el `sentAt`/`ttlMs` de ese frame. El mecanismo completo, con el código del firmware, está en [TTL y Watchdog](/es/safety/ttl-watchdog/) — esa página describe lo que realmente ocurre en el hardware.

## `createControlFrame()`

El protocolo provee una función helper que construye el frame desde un `ControlState`:

```typescript
export function createControlFrame(
  state: ControlState,
  seq: number,
  now: number,
  ttlMs: number = CONTROL_TTL_MS,
): ControlFrame {
  return {
    v: PROTOCOL_VERSION,
    type: 'control',
    seq,
    sentAt: now,
    ttlMs,
    throttle: state.throttle,
    steering: state.steering,
    gripper: state.gripper,
    armed: state.armed,
  };
}
```

Copia el estado de conducción desde el engine, asigna el próximo número de secuencia, estampa la hora actual, y setea el TTL. El navegador nunca construye frames a mano — siempre pasa por esta función, que asegura que cada frame tenga la forma correcta.

## Qué viene antes

ControlSender decide enviar. Llama a `decideSend()` contra el ritmo y recibe una decisión: `immediate`, `rate`, `heartbeat`, o `skip`. Si la decisión no es `skip`, el sender le pide al protocolo crear un frame desde el estado actual del engine.

## Qué viene después

El transporte WebSocket codifica el frame como JSON y lo envía por el cable. El relay lo recibe, estampa `controlSessionId`, y lo reenvía al dispositivo. El firmware valida el frame — revisa `v`, verifica que `controlSessionId` coincida con la sesión activa, aplica el equivalente de `isNewerFrame()` (`seq <= lastSeq` se rechaza), y solo entonces aplica el estado de conducción a los motores. La expiración por TTL se verifica por separado, con el reloj propio del firmware, independientemente de cualquier frame individual — no como una de estas verificaciones por frame.
