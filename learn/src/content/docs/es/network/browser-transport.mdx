El navegador no habla directamente con el robot. Habla con el **relay** — y el relay habla con el robot. La mitad de esa conversación del navegador vive en `WebSocketTransport`.

## Qué hace WebSocketTransport

`WebSocketTransport` (`web/src/transport/websocket.ts`) maneja una única conexión WebSocket al relay. Se encarga de:

- **Conectar** — abrir el WebSocket
- **Enviar** — control frames, emergency stops, pings
- **Recibir** — telemetry, room state, pongs
- **Reconectar** — cuando la conexión cae

Nunca toca motores, perfiles, o entrada. Es una capa de comunicación pura.

## La URL de conexión

La URL del relay viene de una variable de entorno:

```
VITE_RELAY_URL=wss://rovelink-relay.cuello.dev
```

El navegador abre un WebSocket a:

```
wss://rovelink-relay.cuello.dev/robot/r2/controller
```

La ruta `/robot/r2/controller` le dice al relay:

- Qué robot (`r2`)
- Quién se conecta (`controller` — el navegador)

## Ping y pong

El transporte envía mensajes `ping` periódicos. El relay responde con `pong`. Esto mide el **tiempo de ida y vuelta (RTT)** — cuánto tarda un mensaje en ir y volver.

```ts
// el navegador envía
{ v: 1, type: "ping", id: 42, sentAt: 1725400000000 }

// el relay responde
{ v: 1, type: "pong", id: 42, sentAt: 1725400000000, echoAt: 1725400000050 }
```

RTT = `echoAt - sentAt` = 50ms. No necesita relojes sincronizados — el pong devuelve el `sentAt` del ping.

## Qué pasa cuando reconecta

Las conexiones caen. El WiFi tropieza, la laptop se duerme, el relay se reinicia. Cuando el WebSocket se cierra:

1. El transporte limpia su estado
2. Espera un **intervalo fijo** (actualmente 1.5s)
3. Abre una nueva conexión
4. Si aún no puede conectar, espera el mismo intervalo y vuelve a intentar

RoveLink no entra en un bucle de reconexión apretado. Hace una pausa entre intentos — lo suficiente para no saturar el relay, y lo bastante breve para recuperarse rápido.

```
t=0s:     la conexión cae
t=1.5s:   intento de reconexión 1 (tiene éxito) → reanudar
```

Otros sistemas usan **backoff exponencial acotado** — empezando con un delay corto y duplicándolo tras cada fallo. Ese patrón tiene sentido cuando las interrupciones pueden durar minutos y queremos reducir la agresividad. El transporte de control de RoveLink no lo necesita: las sesiones de control son de corta vida, y un delay fijo mantiene la reconexión predecible.

## La API del transporte

El resto del código del navegador nunca abre un WebSocket directamente. Usa la interfaz del transporte:

```ts
interface Transport {
  connect(): void;
  disconnect(): void;
  send(message: RemoteMessage): void;
  on(event: TransportEvent, handler: () => void): void;
}
```

Los eventos incluyen `device-activity` (algo llegó del robot) y `relay-rtt` (una nueva medición de RTT).

## Qué no sabe el transporte

La capa de transporte nunca toca:

- Dispositivos de entrada (teclado, gamepad)
- Perfiles de control
- El control engine
- Motores o hardware

Solo conoce mensajes en la red. Esta separación significa que podrías cambiar el WebSocket por un transporte diferente (HTTP, WebRTC) sin cambiar el resto del código del navegador.

## takeaway

WebSocketTransport es la capa de comunicación del navegador. Abre un WebSocket al relay, envía y recibe mensajes JSON, y reconecta con un delay fijo cuando la conexión cae.
