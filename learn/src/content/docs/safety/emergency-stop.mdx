## What if the operator needs the robot to stop NOW?

Normal control has gates: session check, seq check, baseline check, armed check, TTL. Each gate exists for a reason. But what if the operator needs to stop _regardless_ of all of them? What if the session is wrong, the seq is stale, the TTL hasn't expired yet, but the robot is heading toward a wall?

Emergency stop exists for this.

## Two gates, not one

Everything below this point describes the **firmware-side** bypass — what happens once an E-stop message has actually reached the device. But it has to get there first, and that first step is not bypassed:

1. **Relay admission gate** — the WebSocket must already be registered and authenticated with the room. An unregistered socket's messages are dropped by the relay before they reach the device at all (`relay/src/room.ts`) — this includes a would-be E-stop.
2. **Firmware bypass** — only once a message clears gate 1 does the firmware's session/seq/baseline-independent handling described below apply.

So "E-stop bypasses every gate" is true of gate 2, the firmware, but not of gate 1 — an E-stop from a connection the relay never admitted never reaches the firmware to be bypassed-through.

## E-stop is a distinct message type

E-stop is not a `ControlFrame`. It is a separate message type: `'emergency-stop'`. From `protocol/src/protocol.ts`:

```typescript
export interface EmergencyStop extends Envelope {
  readonly type: 'emergency-stop';
  readonly sentAt: number;
  readonly reason?: string;
}
```

It deliberately carries no `controlSessionId`, no `seq`, no `armed` flag. It is not a control frame. It is a safety command.

## What E-stop bypasses

E-stop deliberately bypasses:

- Session check — it works even if the session is wrong
- Seq check — it is not ordered against normal control frames
- Baseline check — it works before any baseline is established
- Armed check — it works whether armed or not
- linkAlive — it works even if the link was flagged as dead
- TTL — it is not subject to the watchdog timer

The firmware handler goes straight to safe state:

```cpp
void onEmergencyStopReceived(int64_t sentAt) {
  enterSafeState("emergency");
  transportSendEmergencyStopAck(sentAt);
}
```

No conditions, no gates. Enter safe state, send the ack.

## E-stop is NOT session-stamped

The relay forwards E-stop without adding `controlSessionId`:

```typescript
if (message.type === 'emergency-stop') {
  // Deliberately NOT session-stamped: emergency-stop must work
  // regardless of seq/session on the device side
  this.#forward('device', message);
  return;
}
```

This is intentional. E-stop must work even if the controller has not established a session, or if the session is wrong. Adding a session stamp would make E-stop subject to the session gate, defeating its purpose.

## Controller disconnect sends E-stop

When a registered controller disconnects, the relay sends an E-stop to the device:

```typescript
if (attachment.role === 'controller' && attachment.registered) {
  this.#forward('device', {
    v: PROTOCOL_VERSION,
    type: 'emergency-stop',
    sentAt: Date.now(),
    reason: 'controller-disconnected',
  });
}
```

This is gated on `registered` — an unauthenticated probe that opens a controller connection and immediately disconnects cannot force a spurious emergency stop.

## E-stop vs throttle=0

E-stop is not just "send throttle=0." The distinction:

- **throttle=0** — An ordinary control state. It goes through all gates: session, seq, baseline, armed. If the session is wrong, it is rejected. If the seq is stale, it is rejected. It is a normal driving command that happens to say "stop."
- **emergency-stop** — A distinct safety intent. Once past the relay admission gate above, it bypasses every firmware-side gate — session, seq, baseline, armed. It is not a driving command — it is a safety command.

## The firmware always emits an ACK — receipt is a different question

The firmware side of E-stop is unconditional: `onEmergencyStopReceived()` always calls `transportSendEmergencyStopAck()` immediately after entering safe state, with no gate that could suppress it. That's a guarantee about **emission**.

It is not a guarantee about **receipt**. The ack travels back over the same best-effort WebSocket path as telemetry — forwarded once by the relay, with no ack-of-ack and no retry if the browser's connection is momentarily down. If the link is bad enough that the ack doesn't make it back, the robot has still stopped; the operator's UI just doesn't have confirmation of that fact yet.

```typescript
export interface EmergencyStopAck extends Envelope {
  readonly type: 'emergency-stop.ack';
  readonly sentAt: number;
}
```

The `EmergencyStopAck` echoes the triggering message's `sentAt` — not `seq`, because E-stop is session/seq-independent. The browser uses this to match the ACK against its pending E-stop RTT measurement, when it arrives.
