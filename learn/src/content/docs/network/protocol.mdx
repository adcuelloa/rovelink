Every message between browser, relay, and device follows the same format: a **versioned envelope** with a `type` discriminator. The protocol lives in `protocol/src/protocol.ts`.

## The envelope

Every message starts with:

```json
{ "v": 1, "type": "..." }
```

- `v` — protocol version (currently `1`). If the protocol changes, the version bumps. Old firmware keeps working because it can check `v` before processing.
- `type` — which message this is. The rest of the fields depend on `type`.

This is a **discriminated union** — the `type` field tells you exactly what shape the rest of the message has.

## Why version the protocol?

The firmware runs on ESP32 hardware that can't always be updated. If the protocol changes, old firmware still needs to understand (or at least reject gracefully) new messages. The `v` field makes this possible.

In practice, `v: 1` is the only version RoveLink has ever used. But the field is there for when it's needed.

## Message types

Here's the full taxonomy:

### Registration (handshake)

- `device.register` — robot announces itself
- `controller.register` — browser requests control

### Control (driving)

- `control` — throttle, steering, gripper, armed state
- `emergency-stop` — immediate halt, session-independent
- `controller.session` — relay tells the device which session is active

### Feedback

- `telemetry` — device reports RSSI, state, last acked seq
- `control.ack` — device confirms it applied a control frame
- `emergency-stop.ack` — device confirms it applied an emergency stop

### Presence

- `room` — broadcast of who's online

### Video

- `controller.videoTicket.request` — browser requests a video ticket
- `controller.videoTicket` — relay sends the ticket back

### Ping

- `ping` — browser measures round-trip time
- `pong` — relay echoes the ping back

## The ControlFrame

The most important message is `control`. It carries:

```json
{
  "v": 1,
  "type": "control",
  "seq": 42,
  "sentAt": 1725400000000,
  "ttlMs": 500,
  "throttle": 0.72,
  "steering": -0.18,
  "gripper": "open",
  "armed": true
}
```

Key fields:

- **`seq`** — sequence number. Higher always wins. Old frames with lower `seq` are discarded.
- **`sentAt`** — the browser's clock when the frame was created.
- **`ttlMs`** — time-to-live. After this many milliseconds, the robot ignores the frame.
- **`throttle`/`steering`** — the driving intent, -1 to 1.
- **`armed`** — whether motors are enabled.

The `sentAt`/`ttlMs` pair is what the protocol package's `isFrameExpired()` helper uses to detect a stale command — but the real ESP32 firmware does not call that helper or read these two fields when applying a frame. The device's actual link watchdog runs on its own clock instead. The full details, including this distinction, are covered in the Safety module.

## Validation

The firmware validates every incoming message before acting on it:

1. `v` must match `PROTOCOL_VERSION`
2. `type` must be recognized
3. Required fields must be present and the right type
4. `controlSessionId` must match the active session

If any check fails, the message is silently dropped. The firmware never trusts the other end — this layer is defense-first.

## Key takeaway

The protocol is a versioned, typed envelope format. Every message has `v` and `type`. The `control` frame carries throttle, steering, gripper, armed state, and a `sentAt`/`ttlMs` pair — the device's actual link watchdog is a separate, local-clock mechanism, covered in the Safety module.
